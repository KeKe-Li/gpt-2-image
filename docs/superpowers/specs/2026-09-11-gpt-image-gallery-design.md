# GPT Image 灵感库完整迁移与优化设计

## 1. 背景与目标

当前仓库是空 Git 仓库。`KeKe-Li/gpt-2-image` 是一个基于 React、Vite、Vercel Serverless Functions 与 Supabase 的完整案例库产品，包含图片案例、提示词模板、GPT Image 2.5 专区、登录、收藏、在线生成、会员积分、支付、社群和管理后台。

首版迁移固定以上游提交 `073d105d4dbb3f3afcd2e7cd194cee3a557b0999`（提交时间 2026-09-09T08:31:41Z）为基线。该提交的递归文件树包含 723 个文件，其中 `data/cases.json` 声明 541 个案例、13 个分类、19 个风格、10 个场景，`data/images/` 下有 571 个资源文件，另有 21 个 `src/` 文件、49 个 `api/` 文件和 13 个数据库迁移。后续上游变化不计入首版完成标准，只通过同步工具处理。

本项目以该仓库为功能与数据基线，在 MIT License 要求下完成独立品牌化迁移，并针对可维护性、性能、安全性、可访问性和移动端体验进行优化。产品临时名称为“GPT Image 灵感库”，英文名为“GPT Image Gallery”，项目标识为 `gpt-image-gallery`。

## 2. 已确认范围

### 2.1 必须实现

- 完整导入上游案例、图片、分类、标签、模板和来源信息。
- 公开站：精选内容、搜索、分类/风格/场景筛选、案例列表、案例详情、提示词复制、多语言、GPT Image 2.5 对比专区、Skill 与模板入口。
- 用户系统：Supabase 邮箱 OTP（验证码或魔法链接，由环境配置决定，首版默认魔法链接）与 Google OAuth。
- 用户数据：资料、收藏、生成历史、积分、会员、订单和交易记录。
- 在线生成：OpenAI 官方 API 与 APIMart 双 Provider。
- 计费：Stripe 与支付宝双渠道，统一订单、积分包、会员和退款状态。
- 社群购买与状态查询，但不复用上游商户、二维码或推广账号。
- 管理后台：用户、积分调整、订单、退款、生成任务和运营指标。
- 部署：Vercel + Supabase，提供完整环境变量示例和迁移说明。
- 上游同步：完整本地快照，提供可预览差异、校验后人工确认的同步工具。

### 2.2 明确不做

- 不沿用上游品牌、Logo、统计 ID、推广链接、商户账号或 OAuth 应用。
- 不在代码、示例数据或浏览器端写入真实密钥。
- 不自动覆盖本项目人工修改过的案例元数据。
- 不在 Provider 失败后无条件自动切换，避免重复生成与重复计费。
- 不在本轮执行生产部署、数据库生产迁移、真实支付或真实图片生成。

## 3. 产品结构与视觉设计

### 3.1 公开站：编辑策展型

公开首页采用温暖浅色、克制排版和图片优先的编辑策展风格。首屏突出品牌主张、全局搜索、精选案例和“浏览案例/开始生成”两条主行动路径。案例列表使用响应式瀑布流或稳定比例网格，筛选栏在桌面端吸顶，在移动端收纳为抽屉。

公开导航包含：发现、GPT Image 2.5、模板、Agent Skill、定价、登录。案例详情采用大图与结构化提示词并列布局，移动端改为纵向；复制、收藏、基于此案例生成是主要操作。

### 3.2 登录后：创作工作台型

登录后的生成、收藏、历史、账单、账户与后台采用侧栏工作台结构。公开浏览与工作台共享设计令牌、导航状态和用户状态，但页面骨架分离，避免公开站被后台功能挤压。

### 3.3 响应式与可访问性

- 支持 360px 起的移动端布局。
- 所有对话框具备焦点管理、Esc 关闭和滚动锁定。
- 图片包含有意义的替代文本，交互元素支持键盘操作。
- 颜色对比符合 WCAG AA 的主要文本要求。
- 尊重 `prefers-reduced-motion`，避免无意义的大幅动效。

## 4. 前端架构

不延续上游单个超大 `src/main.jsx` 的组织方式。采用按领域拆分的 React 结构：

- `app/`：应用入口、路由、Provider 和错误边界。
- `features/gallery/`：案例列表、筛选、搜索、详情和收藏。
- `features/generation/`：生成表单、Provider 选择、任务轮询和历史。
- `features/auth/`：登录、回调和会话管理。
- `features/billing/`：套餐、积分、结算、订单与退款展示。
- `features/account/`：资料、收藏和交易记录。
- `features/admin/`：用户、订单、生成任务和统计。
- `features/templates/`、`features/skills/`、`features/community/`：独立内容域。
- `components/`：无业务依赖的通用 UI。
- `lib/`：Supabase 客户端、API 客户端、国际化、校验和格式化。
- `data/`：生成后的站点数据与风格库，不在组件中嵌入大体积数据。

公开路由按页面切分代码。后台、账单、生成和 GPT Image 2.5 专区采用懒加载。搜索与筛选使用可测试的纯函数，URL 查询参数保存可分享的筛选状态。

## 5. 服务端与数据边界

### 5.1 API 分层

- 路由处理层：解析请求、认证、限流、响应格式。
- 领域服务层：生成、计费、积分、订单、收藏和管理逻辑。
- Provider 适配层：OpenAI、APIMart、Stripe、支付宝、Supabase。
- 数据访问层：封装数据库读写与事务调用。

所有服务端 API 使用统一错误结构、请求 ID 和安全日志。前端不得决定积分扣减、订单成功或管理员权限。

### 5.2 图片生成 Provider

统一接口包含：创建任务、查询任务、标准化结果、取消或标记失败、估算成本。生成记录保存 Provider、模型、输入参数、输出资源、供应商任务 ID、状态、成本快照、错误码和时间戳。

默认 Provider 由服务端环境变量或管理配置确定。仅在能够确认远端任务未创建时允许自动重试；超时或状态未知时进入人工可审计状态，禁止盲目切换渠道。

OpenAI 与 APIMart 均只从服务端读取密钥。浏览器端只与本项目 API 通信。

生成计费使用版本化价格目录，键由 Provider、模型、尺寸、质量和操作类型组成，值为积分价格与货币成本快照。请求进入时先创建幂等键，并在数据库原子事务中预占预计积分；Provider 明确受理后任务进入 `submitted`。成功时按任务创建时的价格快照结算；明确失败或用户在提交前取消时释放预占；Provider 状态未知或超时时保持预占并进入 `reconcile_required`，由查询任务或管理员对账后再结算或释放。任何重试复用同一幂等键，不得产生第二次扣费。

取消规则以供应商最终状态为准：Provider 未受理时可立即取消并释放预占；Provider 已受理时仅提交取消请求，任务进入 `cancel_requested`，暂不释放积分。供应商确认取消且未产生计费结果后释放预占；供应商拒绝取消或最终仍返回图片时按成功任务结算并保存结果；取消状态长期未知时进入 `reconcile_required`，只能通过对账或管理员审计结算。

### 5.3 认证与权限

Supabase Auth 支持邮箱 OTP 与 Google OAuth。邮箱 OTP 共用一套登录入口，部署环境通过 `VITE_EMAIL_AUTH_MODE=magic_link|code` 选择魔法链接或六位验证码，默认 `magic_link`；测试覆盖两种回调流程。数据库通过 RLS 隔离用户资料、收藏、生成任务、积分和订单。管理员权限由服务端读取受保护角色信息，不接受前端传入的管理员标志。

### 5.4 订单、积分与支付

Stripe 与支付宝共用内部订单模型，但保留各渠道原始标识和状态。Stripe 会员使用自动续费订阅；支付宝会员使用固定期限的一次性购买，不实现自动代扣。支付宝首版固定使用电脑网站支付产品 `alipay.trade.page.pay`，移动端沿用支付宝返回的跳转页面，不另接手机网站支付或当面付。积分包在两个渠道均为一次性商品。支付通知必须验签、幂等处理，并在数据库事务或原子函数中完成“订单更新 + 权益发放”。浏览器支付返回页仅用于展示和主动查询，不直接发放积分。

Stripe 订阅内部状态为 `incomplete`、`active`、`past_due`、`cancel_at_period_end`、`canceled`、`expired`。首次付款与续费成功后生效或延长会员周期并发放当期权益；续费失败进入 `past_due`，在 Stripe 配置的催收宽限期内保留会员访问但不重复发放新周期积分；恢复付款后按对应账期只发放一次。用户取消默认设置为周期末取消，当前周期权益保留到期；立即取消、供应商撤销或退款进入人工审核，根据未使用权益决定是否提前终止。所有 Stripe 事件按事件 ID 幂等，并以订阅 ID、账期起止时间唯一约束阻止重复发放。

退款同样通过幂等状态机处理。未使用的积分包可以全额退款并冲销对应积分流水；积分已部分或全部消费、会员已生效或存在跨周期权益时，不自动退款，进入管理员审核。批准退款时按退款时剩余可回收权益生成负向流水，不允许把余额扣成负数；不足部分记录为人工审计项。订单保存币种、金额、商品快照、支付渠道、商户订单号、供应商交易号、状态变化和审计时间。

社群商品定义为一次性购买商品，可使用 Stripe 或支付宝。支付成功后状态进入 `paid_pending_fulfillment`，管理员在后台填写交付说明或配置化入群链接并标记 `fulfilled`；用户账户中心显示交付状态。首版不接入上游二维码或自动拉群服务。

## 6. 数据模型

核心实体包括：

- `profiles`：用户资料与角色引用。
- `case_favorites`：用户收藏，用户与案例组合唯一。
- `generation_tasks`：生成请求、Provider、状态、参数和成本。
- `credit_ledger`：不可变积分流水，余额由原子过程维护或从流水校验。
- `products`：会员与积分商品配置。
- `orders`：统一内部订单。
- `payment_events`：去重后的支付通知原文摘要与处理结果。
- `memberships`：会员状态和有效期。
- `admin_audit_logs`：管理员敏感操作记录。
- `community_orders`：社群商品和发放状态。

沿用并整理上游 Supabase migrations，新增迁移必须可重复部署、可回滚评估，并补充 RLS 策略测试。

公开案例图片随站点静态资源发布；用户生成图片保存到 Supabase Storage 的私有 `generated-images` bucket。数据库只保存对象路径和元数据，前端通过短时签名 URL 访问。默认保留 30 天，可由环境配置调整；用户可主动删除自己的生成图片，删除操作同步清理 Storage 对象并在任务记录中保留不含图片内容的审计状态。Provider 临时 URL 只用于服务端抓取，不作为长期结果地址。Vercel Cron 每日分批清理到期对象，失败项记录重试次数；另设孤儿对象与失效数据库引用的只读对账任务，管理员确认后才执行修复。

## 7. 案例数据与同步

案例数据在构建前由脚本生成面向站点的轻量 JSON。同步工具执行以下阶段：

1. 拉取指定上游提交的元数据清单。
2. 生成新增、修改、删除和冲突报告，不直接覆盖。
3. 校验 ID 唯一性、必填字段、图片链接、文件哈希、尺寸和格式。
4. 保留本地覆盖字段和来源信息。
5. 用户显式确认后写入数据和资源。

同步结果记录上游仓库、提交 SHA、同步时间和变更摘要。生产运行不依赖上游网络。

首版迁移验收清单固定为：541 个案例、13 个分类、19 个风格、10 个场景、571 个 `data/images/` 资源。同步校验报告必须列出源文件总数、成功导入数、去重数、缺失数、哈希不一致数和未识别字段；校验每个案例的标签集合、来源字段及图片关联，输出缺失字段和孤儿标签清单；任何缺失或无法解释的数量差异都使迁移验收失败。模板、Skill、许可证和来源文件单独列入清单并校验存在性。

### 7.1 多语言策略

首发支持简体中文 `zh-CN` 与英文 `en`，默认根据浏览器语言选择，无法判断时使用简体中文；用户选择保存在本地。公开可索引页面使用 `/zh-CN/...` 与 `/en/...` 路径，设置正确的 `lang` 与 `hreflang`。界面文案必须完整双语；案例标题、说明、分类和标签保留上游已有双语字段，缺少翻译时回退原文并显示原始语言，不自动机器翻译。提示词始终保留原文，可附独立翻译字段但复制默认复制原始提示词。

## 8. 性能设计

- 图片按展示尺寸生成多规格资源，优先 WebP/AVIF，并保留必要原图。
- 首屏精选图预加载，其余图片懒加载。
- 大型案例数据按搜索索引与详情数据拆分，避免首屏加载完整提示词正文。
- 路由和重型业务模块代码分割。
- 搜索输入防抖，筛选计算使用预构建索引，避免重复全量扫描。
- API 设置合理超时、重试边界和缓存头。
- Vercel 构建输出中检查大资源和异常 chunk。

## 9. 安全与隐私

- 环境变量按公开/服务端分组；只有明确标记为公开的配置进入前端构建。
- 支付、生成、管理接口进行认证、授权、输入校验、速率限制和请求体大小限制。
- 日志不记录 API Key、支付密钥、完整用户令牌和敏感支付原文。
- 外部回调验证签名、时间窗口、事件唯一性和允许的状态迁移。
- 用户提供的提示词与图片链接按隐私数据处理，默认不用于公开案例。
- 增加 CSP、安全响应头和外链 `rel` 策略。

## 10. 错误处理与可观测性

- 页面级错误边界提供重试与回到首页入口。
- 网络错误、权限错误、额度不足、Provider 拒绝和任务超时分别展示可操作提示。
- 每个生成、支付和管理员操作携带请求 ID。
- 管理后台可查看失败任务、异常订单和待人工处理状态。
- 统计能力通过独立适配器接入，不写死上游 GA 配置；未配置时不加载跟踪脚本。

管理后台首版指标固定为：注册用户数、活跃用户数、生成任务数与成功率、按 Provider 的失败率和成本、积分发放与消耗、订单金额与支付成功率、退款数量、热门案例和收藏次数。其他指标不进入首版范围。

## 11. 测试与验收

- 单元测试：筛选、搜索、国际化、金额计算、状态机、Provider 标准化与签名校验。
- API 测试：认证、幂等、权限、异常映射和支付/生成回调。
- 组件测试：案例卡片、筛选器、详情、登录、生成表单和账单状态。
- 端到端测试：浏览案例、登录回调模拟、收藏、生成任务模拟、支付回调模拟和管理员权限。
- 构建检查：类型/语法、lint、测试、生产构建、资源体积和无密钥启动。
- 测试命令单次执行控制在 60 秒以内；较慢套件拆分执行。

验收时必须证明：无真实密钥也能启动公开站；完整迁移清单数量与哈希校验通过；配置测试密钥后各 Provider 可独立启用；禁用任一支付或生成 Provider 不影响其他功能；普通用户无法调用管理接口；重复支付通知不会重复发放权益；核心页面在桌面和移动端均可用。

## 12. 迁移实施策略

采用“保留数据与业务语义、重建应用边界”的方式，而非直接长期维护上游单文件结构：

1. 导入许可证、数据、图片、脚本、迁移和可复用服务逻辑。退出条件：固定基线清单与哈希校验通过。
2. 建立新的应用骨架、设计令牌、路由和领域目录。退出条件：无外部密钥可启动并通过基础构建。
3. 恢复公开案例库，再接入认证与收藏。退出条件：双语、搜索筛选、详情、登录与 RLS 测试通过。
4. 接入双生成 Provider 与生成记录。退出条件：模拟 Provider 覆盖成功、失败、超时、幂等和积分结算。
5. 接入商品、积分、Stripe、支付宝和社群。退出条件：测试环境支付回调、重复通知、退款审核和交付状态测试通过。
6. 重建账户中心与管理后台。退出条件：普通用户越权测试失败、管理员审计记录完整、最小指标集可查询。
7. 完成性能、安全、响应式、测试和部署验证。退出条件：生产构建通过、关键页面移动端验证通过、部署文档和环境变量清单完整。

每个阶段保留可运行状态，并通过自动化测试阻止回归。

## 13. 外部配置与降级行为

缺少 Supabase、OAuth、OpenAI、APIMart、Stripe 或支付宝配置时，应用不得崩溃：

- 公开案例库始终可用。
- 未配置的登录、生成或支付入口显示“尚未配置”，并从可选操作中安全禁用。
- 管理后台明确展示 Provider 健康与配置状态，但绝不显示密钥内容。
- 示例环境变量只提供字段名和说明，不提供真实值。
